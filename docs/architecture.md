# Architecture

`src/chihiros_led_control/` is the source of truth for the reusable Python
library and CLI. Home Assistant code lives in
`custom_components/chihiros/` and imports a vendored runtime copy of that
library.

The vendored package at
`custom_components/chihiros/vendor/chihiros_led_control/` keeps HACS installs
self-contained. Do not edit vendored files directly. Make library changes in
`src/chihiros_led_control/`, then run:

```bash
uv --cache-dir .uv-cache run python scripts/sync_vendor.py
```

CI checks the copy with:

```bash
uv --cache-dir .uv-cache run python scripts/sync_vendor.py --check
```


## Device architecture

The runtime follows a metadata-driven family flow:

```text
models/profile types
        ↓
registry.py (advertised prefix → DeviceModel)
        ↓
factory.py (DeviceModel.spec → family driver)
        ↓
devices/ (LED, dosing, stirrer, heater)
        ↓
protocol/ (shared frames plus family codecs)
        ↓
transport.py (BLE lifecycle boundary)
```

`DeviceModel.spec` separates product identity from behavior. `DeviceKind`,
`LedProtocol`, and `LedFeature` are discriminators; family selection never
uses a display name. `ChihirosDevice` remains the public LED client, while
dosing pumps, magnetic stirrers, and heaters are selected as separate family
drivers.

`src/chihiros_led_control/` is canonical. The integration vendor copy is
generated by `scripts/sync_vendor.py`; do not edit it directly.

## Public module boundaries

Applications resolve devices through the package-level exports:

```python
from chihiros_led_control import ChihirosDevice, create_device
from chihiros_led_control.devices import ChihirosDosingPump, ChihirosHeater, ChihirosMagStirrer
from chihiros_led_control.protocol import frame, notifications
from chihiros_led_control.protocol import dosing, heater, led, stirrer
```

`protocol.frame` owns framing, message IDs, and checksums. `protocol.notifications`
owns notification value objects and the parsed-notification union. `protocol.led`,
`.dosing`, `.stirrer`, and `.heater` own family command and parser behavior. The
base driver owns only identity, transport submission, lifecycle, and notification
dispatch hooks; family drivers own parsing and persistent notification state.
Shared dosing wire builders support stirrer scheduling and master/slave replay
without making the stirrer a dosing-pump client. The old monolithic client and
codec modules are not compatibility entry points.

Home Assistant development fakes are organized under
`custom_components/chihiros/fake/`, with separate LED, dosing, stirrer, and
heater implementations selected from the fake registry. They mirror the
family-specific runtime surfaces instead of exposing one broad fake client.
## Schedule replacement failures

The BLE protocol exposes reset and add operations but no atomic replacement or
reliable read-back suitable for rollback. `set_schedule` validates the complete
replacement before resetting the device. If adding any period fails, it
attempts another reset so the result is empty rather than a partial,
unpredictable schedule, then raises a Home Assistant error explaining that the
old schedule cannot be restored. If that cleanup reset also fails, the error is
logged because the device may contain a partial replacement.
